Nested Loop
小表驱动大表，性能最佳。小表被Scan，大表被Seek。
Foreach(SmallRow in SmallInput)
{
	Foreach(BigRow in BigInput)
	{
		if(SmallRow=BigRow)
			Output;
	}
}

Merge Join
双方的Key都已被排序。两边数据量相仿。
R1=first row from Input1;
R2=first row from Input2;
While(end of Input1) and (end of Input2)
{
	if(R1=R2)
	{
		Output;
		R2 = next row of Input2;
	}
	else if(R1<R2)
	{
		R1 = next row of Input1;
	}
	else
	{
		R2 = next row of Input2;
	}
}
Hash Join
在两个大的数据集合之间
1.选出较小的那张表。
2.Hash较小表的Key存入Bucket
3.查看较大表中的每条记录，Hash Key
4.与每个Bucket中的每个Hash Value比较。
Foreach(R1 in Input1)
{
	H1=HashValue(R1.Key);
	Insert H1 into HashBucket;
}
Foreach(R2 in Input2)
{
	H2=HashValue(R2.Key);
	Foreach(H1 in HashBucket)
	{
		if(H1=H2)
			Output(R1,R2);
	}
}

4.2.2内存中的数据
数据库服务刚启动，会自动将一些数据放入内存Buffer Pool。
Buffer Pool一次由一个线程访问。只有将数据放入缓存才能被数据库操作。

1.脏数据(Dirty Data)
只在Buffer Pool中被更新，但还没有在磁盘上被更新。
处理Dirty Data的进程叫Check Point。
Check Point每隔固定时间就会被触发。

在数据还脏的时候更新数据库服务会丢失数据吗？
不会。因为有log。里面有Log Sequence Number。

Lazy Write想办法扩大缓存大小。
当快没缓存的时候被触发，不是固定时间内被触发。
Lazy Write = Check Point + 释放内存 （只有内存不够时被触发。check point是为了释放内存）
当然也会在Plan cache里检查太长时间没被用的执行计划，然后清空。

4.3诊断内存瓶颈
当I/O增加，也许说明内存不够。
当总体内存不够时，OS会问SQL OS要内存。SQL Server就会变慢。
本身内存不足：1.外部内存不足。2.修改max server memory。

当I/O和CPU非常高，可能是内存不足。

8.1锁，事务要解决的问题。
数据库的四个基本特征：
Atomicity:一个事务内的操作，要么全部成功，要么全部失败。
Consistency：事务成功前与失败后，business logic要一致。
Isolation：事务与事务之间互不干扰。
Durability：如果数据库此时紧急重启，数据不能丢失。

锁主要要解决的问题：
脏读：T1只是在内存更改数据，但还没Commit，没有更新磁盘。T2读取内存数据。T1回滚。
不可重复读：因为数据更新，在同一事务中，得不到相同结果。
幻读（让财务头疼）:因为插入新数据，导致同一事务中，得不到相同结果。|T1要删除所有数据。T2突然插入新数据。T1发现尽还有条数据没被删。
重复读：在同一事务中，把一条数据读成两条。T1正从前扫到后来读取数据。T2更新了一条记录，使这条记录排到了后面。T1再读一次这条数据。

8.3锁粒度
行锁；页锁；表锁。

8.4锁模式
共享锁：保证多个事务共读一块资源。只读不改，防止被加排它锁。select * from YourTable with(TabLock, HoldLock)
排他锁：
更新锁：先加S锁找寻要更新的数据。找到对象后换成X锁。更新时换成U锁。
意向锁：就像一个信号，表示一个事务想要获取某种锁。当另一个事务想要获取锁时，先要查看资源上是否有意向锁。如果有冲突，就不能获取。
具体的锁作用在细粒度上。意向锁作用在大粗粒度上。
一个事务只要更新一行，另一个事务需要更新一片。为了不产生冲突，就要加意向锁。

查询时，数据引擎会自动加上Schema Stability锁。
修改表结构时，会自动加上Schema Modification锁。

8.9.2死锁报警：一般都是因为query写得不好，效率低，或是因为事务太长。

高并发可能导致的问题：阻塞，资源竞争。
解决方案：Transaction; Lock.

阻塞：锁与锁的互斥会导致某个或某些事务无法获得相应的锁。

2.为什么用自增列作为主键？
表数据存在主键，就是一颗B+树叶子节点上。每节点上有一页，每页有8k。每页的数据都会按顺序排放。
如果用非自增主键，
那数据库首先要为新数据找到一个合适的位置。
如果这个位置不在内存里，那要把数据从磁盘里读出来。
插入新数据。
插入后如果页数据超过8k，还要分页，造成碎片。
如果用自增主键，直接append就可以。
不要找一个合适的位置。
不用造成磁盘I/O。
如果一页放不下，直接开个新页就可以。不会产生分页。

12.Database Normalization
1NF:一个字段必须不能被拆。比如不要把FirstName,LastName放在一个字段内。
2NF:一个表里只能放一种数据。在订单表里有订单信息和产品信息。最好把它拆成两张表。
3NF:表中每个字段都要与主键直接相关。Product表中最多有订单Id，不能再有订单日期。
BCNF:EmployeeInfo(EmployeeID, EmployeeName, ProjectID, ProjectName)
    EmployeeID, ProjectID -> EmployeeName
    ProjectID -> ProjectName
这种情况下，要把它拆成两张表。   
4NF:删除表内多对多关系
StudentCourseInfo(StudentID, CourseID, Instructor, Textbook)
Many students have many courses.
Many courses have many instructors.
Many courses have many textbook.
StudentCourse(StudentID, CourseID)
CourseDetails(CourseID, Instructor, Textbook)

21.索引的有缺点？

缺点：

经常被查询。经常被排序。在主键。在外键。

很少被用来查询，排序的列。数据很少，只有男女。里面还有很多空值。
text,image,bit
经常需要被修改的列。

22.什么样的字段适合建索引？
唯一，非空，经常被查询。
在查询条件中，类型一定要匹配，否则用不到索引！

23.聚集索引与非聚集索引的区别？
一张表只能有一个聚集索引。所有数据页存在聚集索引的叶子上。表记录排列顺序与索引排列顺序相同，所以有最快的查找速度。
一张表可以有多个非聚集索引。非聚集索引有索引字段，PK字段，和Bookmark。与表数据分开存储，像是一本关于这张表的笔记。表记录排列顺序与索引排列顺序不相同。

7). How can you optimize stored procedures?
1. Use the SET NOCOUNT ON statement (When SET NOCOUNT ON is specified, SQL Server does not send the count of the number of rows affected by a T-SQL statement as part of the result set. Reduce the amount of network traffic)
2. Use the schema name with the object name
-- Using schema name with table name
SELECT * FROM dbo.TableName;

-- Using schema name with stored procedure
EXEC dbo.StoredProcedureName;

Avoid Implicit Schema Resolution
If you do not specify the schema, SQL Server will attempt to resolve the object using the default schema associated with the user. 
Relying on implicit schema resolution can lead to confusion and potential issues, especially if the default schema changes.

3. Do not use the prefix "sp_" in the name
4. Use IF EXISTS (SELECT 1) instead of SELECT *
5. Avoid using cursors
Cursors can be less efficient than set-based operations. 一行一行处理, I/O高network traffic高,总体速度变慢, 特别是行数多的时候.
Set-based operations take advantage of SQL Server's optimized query processing and can be more efficient for handling data in batches.
6. Keep the transactions short as possible.
- Use sp_executesql instead of the EXEC statement for dynamic SQL
sp_executesql supports parameterized queries, 
allowing you to define and pass parameters to the dynamic SQL statement. 
This can help improve performance and security by using parameterization to avoid SQL injection.

Q:-2. What are some tips to improve the performance of SQL queries?
1. Prefer to use views and stored procedures in spite of writing long queries. It’ll also help in minimizing network load.

2. It’s better to introduce constraints instead of triggers. They are more efficient than triggers and can increase performance.

3. Make use of table-level variables instead of temporary tables.

4. The UNION ALL clause responds faster than UNION. It doesn’t look for duplicate rows whereas the UNION statement does that regardless of whether they exist or not.

5. Prevent the usage of DISTINCT and HAVING clauses.

6. Avoid excessive use of SQL cursors.

7. Make use of the SET NOCOUNT ON clause while building stored procedures. It represents the rows affected by a T-SQL statement. It would lead to reduced network traffic.

8. It’s a good practice to return the required column instead of all the columns of a table.

9. Prefer not to use complex joins and avoid disproportionate use of triggers.

10. Create indexes for tables and adhere to the standards.
