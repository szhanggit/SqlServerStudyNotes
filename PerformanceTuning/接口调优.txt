接口性能优化：
1. 慢查询汇总接口邮件（接口地址，调用次数，最大耗时，平均耗时，TraceId）
2. 用skywalking查看接口调用信息。
3. 研究瓶颈位置
4. 可以是从索引入手改造searching query。
5. 把单线程调用改成多线程调用。
6. 改变业务逻辑，比如限制每次查询的记录数。 （分批调用接口） 如果每次最高效率是查询100条记录。查500条的时候就分成5批。


有时候：加个索引；代码重构；增加缓存；引入中间件；分库分表；拆分服务。
1. 索引
1.1没加索引（where,orderby）
1.2索引没生效（Execution plan）
	1.不满足最左匹配原则
	2.范围索引列没放到最后
	3.使用了select *
	4.索引列上有计算
	5.索引列上使用了函数
	6.字符类型没加引号
	7.用is null和is not null没注意字段是否允许为空
	8.like查询左边有%
	9.使用or关键字时没注意
1.3选错索引
	1.有时会走索引a，有时会走索引b。（用强制指定索引）
2. SQL优化
	1. 避免使用select * (不会走覆盖索引，而且会返回不需要的数据。)
	2. 用union all代替union (Union会自动排除重复数据，Union all不会自动排除重复数据)
	3. 小表驱动大表（in适用于左边大表，右边小表。exists适用于左边小表，右边大表）
	4. 批量操作
	5. 多用limit(update order set status = 0, edit_time=now(3) where id>= 100 and id < 200 limit 100;)
	6. in中值太多(如果多余500条，就要用多线程分批查询)
	7. 增量查询(select * from user where id>#{lastId} and create_time >= #{lastCreateTime} limit 100;从id入手分批查询)	
	8. 高效的分页(select id, name, age from user where id > 1000000 limit 20;)
	9. 用连接查询代替子查询(子查询会自动产生临时表，消耗IO资源。直接用join会经济很多。)
	10.join的表不宜过多(最好不超过3个，数据库否则难以选对索引)
	11.join时要注意(当用left join时，左边用小表，右边用大表。如果能用inner join，就少用left join。)
	12.控制索引的数量(单表索引数量不要超过5个。)
	13.选择合适的字段类型(企业名称用varchar，电话号码用char。能用数字类型，就不用字符串。用尽可能小的类型，bit,tinyint。金额用decimal)
	14.提升group by的效率(线过滤，再分组。select uer_id, user_name from order where user_id <= 200 group by user_id)
	15.索引优化
3. 远程调用
	1. 用并行调用代替串行调用
	2. 把数据放一部分在redis
4. 重复调用
	4.1如果要查50位用户信息，那要远程调用50次。若能合并在一个batch能一起请求就会提高效率。
	4.2因为代码不严谨导致的死循环。
	4.3无限递归（规定最大深度）
5. 异步处理
	5.1线程池.业务操作（核心逻辑同步执行，同步写库）->发站内通知（非核心逻辑可以异步执行，异步写库）->记录用户日志（非核心逻辑可以异步执行，异步写库）
	核心逻辑可以同步执行，同步写库。非核心逻辑可以异步执行，异步写库。通常异步主要有两种：多线程和message queue。
	5.2Message Queue。如果线程池被重启，那信息就会丢失。这时要用MQ。
6. 避免大事务 （死锁，回滚时间长，并发情况下数据库连接池被沾满，锁等待，接口超时，数据库主从延迟）
	将查询select放到事务外。
	事务中避免远程调用。
	事务中避免一次性处理太多数据
	有些功能可以非事务执行
	有些功能可能异步处理
7. 锁粒度 - 锁的颗粒度不能太粗。
	7.2分布式锁。redis分布式锁。zookeeper分布式锁。
	7.3数据库分布式锁：表锁（速度快，不会死锁，但颗粒度大），行锁（加锁慢，会出现死锁。但颗粒度小），间隙锁。优先使用行锁，然后间隙锁，最后表锁。
8.分页处理 - 分页或分批获取数据。
	8.1同步调用（对耗时要求不高）
	8.2异步调用
9. 加缓存 - 用户下单可以不加缓存。
	9.1 Redis缓存
	9.2 二级缓存
10.分库分表
	分库是为解决数据库连接资源不足和磁盘IO性能瓶颈。（若只是并发量大，可以只分库不分表）
	分表是为解决单表数据量太大，即使走了索引也非常耗时问题，消耗CPU资源问题。（若用户并发量不大，但需要保存许多数据，那只需要分表）

	11.2加监控 - 接口响应时间； 调用第三方服务耗时； 慢查询SQL耗时； CPU使用情况； 内存使用情况； 磁盘使用情况； 数据库使用情况；
	11.3链路跟踪 - 分布式链路跟踪系统skywalking。
